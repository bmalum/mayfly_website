Mayfly

A lightweight AWS Lambda Custom Runtime for Elixir

Write a handler module, run mix release, attach the Erlang layer. No Docker, no boilerplate, no silent failures.

Get Started Read the Guide
🧩

A behaviour, not a string

use Mayfly.Handler, implement handle/3, keep cold-start work in init/1. Compile-time checked.

📦

mix release is the build

Three release steps produce lambda.zip. Umbrellas, multiple releases and runtime.exs just work.

🪶

Erlang layer, no Docker

Public layers ship ERTS. Your zip is a few MB of BEAM files and builds on any OS in seconds.

🛡️

Honest errors

Exceptions, exits, bad return values, unencodable results and wrong handlers all reach Lambda as proper errors with Elixir stack traces.

🌊

Response streaming

Return any Enumerable. Function URL preludes and mid-stream error trailers included.

🧵

Managed Instances

One poller process per concurrency slot. Invocations run in parallel on the BEAM, isolated by design.

🔍

Observable

JSON logs with request and tenant ids, :telemetry events, X-Ray trace propagation.

🪶

Zero dependencies

Built-in JSON, own HTTP client over :gen_tcp. Nothing starts in mix test or iex.

Plain Elixir

The event is a decoded map, the context carries request id, deadline and tenant, the result is JSON.

defmodule MyApp.Handler do
  use Mayfly.Handler

  @impl true
  def init(_opts) do
    # runs once per execution environment
    {:ok, %{table: System.fetch_env!("TABLE_NAME")}}
  end

  @impl true
  def handle(event, %Mayfly.Context{} = ctx, state) do
    {:ok, %{
      message: "Hello, #{event["name"]}!",
      request_id: ctx.request_id,
      remaining_ms: Mayfly.Context.remaining_time_ms(ctx),
      table: state.table
    }}
  end
end

From zero to Lambda in four steps

Requires Elixir 1.18+ and OTP 27+. Pin your OTP to the layer's version, e.g. mise use erlang@27.3.4.18.

1

Add the dependency and a release

# mix.exs
def project do
  [
    app: :my_app,
    deps: [{:mayfly, "~> 1.0.0-rc"}],
    releases: [
      lambda: [
        steps: [&Mayfly.Release.prepare/1, :assemble,
                &Mayfly.Release.bootstrap/1, &Mayfly.Release.zip/1],
        mayfly: [handler: MyApp.Handler, layer: true]
      ]
    ]
  ]
end
2

Write the handler and try it locally

mix lambda.invoke MyApp.Handler '{"name":"world"}'
mix lambda.doctor        # checks release config, handler and OTP vs. layer

mix lambda.invoke runs the real runtime against an in-process Runtime API emulator, so errors, context and streaming behave exactly as in Lambda.

3

Build

MIX_ENV=prod mix release lambda
# * creating _build/prod/rel/lambda/bootstrap
# * creating _build/prod/rel/lambda/lambda.zip (1570 KiB)

Prefer to bundle ERTS instead of using a layer? Drop layer: true and run mix lambda.build --docker --arch arm64 (docker or finch).

4

Deploy

aws lambda create-function --function-name hello \
  --runtime provided.al2023 --architectures arm64 \
  --handler MyApp.Handler \
  --layers arn:aws:lambda:REGION:ACCOUNT:layer:mayfly-erlang-27-arm64:1 \
  --zip-file fileb://_build/prod/rel/lambda/lambda.zip \
  --role arn:aws:iam::ACCOUNT:role/lambda-role

Handler is the module name. Works with SAM, CDK and Terraform; snippets are in the deployment guide.

Erlang runtime layers

BEAM files are architecture independent; only the Erlang runtime is not. Mayfly ships it as a Lambda layer, rebuilt weekly for the latest patch of each supported OTP major, both architectures, 16 regions.

Pinned

mayfly-erlang-27-3-4-18-arm64

One OTP patch release. Pin the full ARN in your infrastructure.

Alias

mayfly-erlang-27-arm64

Newest version always tracks the latest 27.x patch.

Your own

layer/build.sh && layer/publish.sh

Publish to your account or AWS Organization in minutes.

The bootstrap verifies the layer's ERTS matches your build before starting the VM, so a version mismatch fails with a readable message. Current ARNs: ARNS.md on the layers release · layer guide

Built for how Lambda works today

Implements the current Runtime API: invocation ids are echoed, tenant ids land in the context, error types follow Lambda's Category.Reason convention so the console classifies them correctly.

On Lambda Managed Instances a single environment serves AWS_LAMBDA_MAX_CONCURRENCY invocations in parallel, each in its own process. Verified on real hardware: eight concurrent invocations, one VM.

Cold start is BEAM boot: about half a second from the layer with a stripped release, single-digit milliseconds warm, ~85 MB resident.

Misconfigured handler? The function fails to start and Lambda says Runtime.NoSuchHandler. Nothing is ever reported as a success that was not one.
